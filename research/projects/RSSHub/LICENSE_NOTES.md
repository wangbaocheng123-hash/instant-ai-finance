## 场景初判

| 场景 | 初步风险 | 建议 |
|---|---|---|
| 个人本机运行未修改 RSSHub | 低于修改/分发场景，但仍遵守许可证和来源条款 | 可进入运行验证 |
| 独立 localhost sidecar，通过标准 RSS/HTTP 接入 | 边界较清晰；是否构成更广泛组合作品仍需法律确认 | 当前首选 |
| 修改 RSSHub 后提供网络服务 | 明确触发第 13 节关注点 | 提供对应源码与显著入口；法律评审 |
| 把 RSSHub npm 包嵌入闭源桌面核心 | 组合与衍生作品风险更高 | 当前 `REJECT`，未经评审不做 |
| 复制 Route/核心源码到即时 AI | 混合许可证、持续归因与对应源码风险 | 禁止直接复制 |
| 只参考抽象模式，自行独立实现接口 | 风险相对低，但需避免实质复制 | 保留研究证据，独立设计 |

## 第三方内容与依赖不是自动清零

AGPL 只解决 RSSHub 代码许可证问题，不代表：

- 上游网站内容可以任意抓取、保存或再分发；
- Cookie、登录账号、付费内容可以绕过授权限制；
- RSSHub 的全部 npm 依赖与第三方 SDK 都只有同一许可证；
- 商标、数据库权利、隐私和站点条款没有约束。

正式采用前还需输出：依赖许可证清单、启用 Route 白名单、来源使用条款与内容保存策略。

## 对即时 AI 的许可证边界建议

1. RSSHub 独立目录、独立进程、独立许可证和版权通知。
2. 不修改上游快照；需要补丁时建独立 Fork/patch 目录并保存提交和来源。
3. 客户端仅通过 localhost HTTP/RSS/JSON Feed 交换标准数据。
4. UI 中保留 RSSHub 归因、源码和许可证入口；具体做法待法律确认。
5. 所有自有持久化、AI、评分和 UI 代码不从 RSSHub 复制实现。
6. 若分发包含 RSSHub 的安装包或修改版，发布前单独进行 AGPL 合规审查。
