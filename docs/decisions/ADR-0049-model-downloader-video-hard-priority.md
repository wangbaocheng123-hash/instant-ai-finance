# ADR-0049：模型下载器一分钟视频硬优先调度

- 状态：`ACCEPTED / IMPLEMENTED IN MAIN / PRODUCTION PENDING`
- 日期：2026-09-11
- 决策者：产品所有者

## 背景

ADR-0048 把模型先生主页改为全天运行并把循环尾部等待设为 3 分钟，但旧循环把主页扫描、
新视频下载、全部到期评论和全部修复任务放在同一轮中。等待时间只在整轮结束后开始，因而
一条评论可能占用 3 分钟，多条评论可把下一次主页检查推迟到几十分钟以后；“3 分钟”并不
等于每 3 分钟检查主页。

2026-09-11 生产核验还发现，前次用于发布取码的一次性 SOCKS 代理虽然已从 systemd
manager 清除，旧模型下载器进程仍继承了四个代理环境变量。临时隧道关闭后，主页检查从
2026-09-10 22:27 至 2026-09-11 07:30 连续失败。07:30 重启清除进程残留代理后，07:31
主页扫描恢复；但随后评论抓取从 07:31 持续占用到 07:36，再次证明调度结构会阻塞视频。

## 决定

1. 新视频是模型下载器的硬优先级任务。主页检查和发现后的完整视频下载构成独立视频轮次，
   其中不执行评论、历史修复或其他维护工作。
2. 全天以每次主页检查的**开始时间**为基准，每 1 分钟安排下一次检查。正常主页扫描约
   10–12 秒；1 分钟是当前 Chromium 方案兼顾删除前捕获、服务器负载与平台风控的持续运行
   下限。若扫描或新视频下载超过 1 分钟，完成后立即开始下一次检查，不再额外等待 1 分钟。
3. 评论和手工音视频修复只能使用两次视频检查之间的空档。每个空档最多处理一项维护任务，
   预留 8 秒释放 Chromium；到截止时间即取消维护，让下一轮视频检查先执行。评论每个空档
   最多运行 35 秒并保存已取得的增量结果。
4. 视频检查失败时不运行任何评论或修复；连续失败至少 3 次写入 critical 日志，下一周期仍
   只优先重试视频。既有“发布后未满 24 小时每 15 分钟、之后每 60 分钟”的评论到期规则
   继续作为目标频率，但在资源冲突时必须服从视频检查。
5. 模型下载器两个 systemd 单元显式清除大小写 HTTP/HTTPS/ALL proxy 环境，防止以后任何
   一次性发布代理泄漏到业务进程。
6. 北京模型下载器发布器不再只凭进程 `active` 判定成功；新版本重启后必须在 SQLite 中看到
   一个晚于发布标记且成功完成的真实主页检查，否则在 100 秒内回滚。
7. 版本升级为 `0.9.2+git.video-priority`。本决定先进入 `main`；只有所有者明确要求正式
   发布北京采集套件后，才推进 `beijing-production`。

## 即时处置

在正式版本上线前，生产旧版通过 systemd manager 临时设置
`MODEL_DOWNLOADER_COMMENTS_ENABLED=0` 并重启，只保留 3 分钟视频循环。07:36、07:39
主页检查连续成功；07:39 发现一条 07:37 发布的新作品，07:40 完成有声 MP4 下载。该
临时变量须在 0.9.2 正式发布时清除，恢复由新调度器受控的评论空档。

## 边界

- 不并发启动两个共享浏览器 profile 的 Chromium，不用并发换取表面速度。
- 不修改视频、评论、数据库、Cookie、登录资料或已有媒体；临时中断的评论失败不推进成功
  游标。
- 不把 1 分钟解释为绝对零延迟：通常发现延迟约为 0–70 秒，极短时间内发布后删除的作品
  仍可能无法恢复。
- 本决定不修改北京博主采集器、新加坡即时 AI、时变罗盘、DNS、Caddy 或付费模型任务。
